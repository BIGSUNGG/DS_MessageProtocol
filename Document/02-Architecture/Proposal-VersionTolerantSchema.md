# 제안: 버전 내성 스키마 (Version-Tolerant Schema)

> **상태: 기각 (2026-09-09)** — [ADR-0006](../05-Decisions/ADR-0006-No-Schema-Evolution.md). Unity·서버가 같은 라이브러리를 함께 소비하는 이 프로젝트에는 버전 혼합 피어가 없어 스키마 진화 자체가 불필요.
> 근거·설계 옵션은 참조용으로 보존한다. 배포 환경이 바뀌면(외부 배포·제3자 클라이언트) 새 ADR 로 재검토.

## 문제 (왜 게임 서버 운영에 실제 필요한가)

라이브 서비스는 롤링 배포·클라이언트 강제 업데이트 불가 환경(콘솔·심사 지연)에서
**서로 다른 스키마 버전의 피어가 통신한다**. 현재 와이어 형식은 위치 기반(positional)이라:

- 수신측에 없는 **새 필드**를 발신측이 추가하면 → 필드 밀림으로 전체 프레임 오염(진단은 KI-5 헤더 검증에서 끝남).
- 수신측이 아는 **삭제된 필드** → 같은 이유로 오염.

즉 스키마 변경 = 배치 동기화 강제. 현재의 유일한 완화는 상위(DS_RPC)가 모든 변경을 부가 필드로 우회하는 것 —
계속 쌓이는 레거시 필드와 `null` 관례라는 기술 부채로 귀결된다.

## 설계 옵션

### 옵션 A — 필드 태그 + 길이 접두 (protobuf 방식, 권장)

- 멤버마다 `[MessageMember(Tag = n)]`(기존 선언 순서 → 태그 자동 부여로 마이그레이션 가능).
- 와이어: `tag-wiretype 바이트 + (가변형만) 길이 접두 + 페이로드`.
- 판독: **모르는 태그는 wire-type 으로 길이를 계산해 Skip** — 상위 호환이 구조적으로 성립.
- 비용: 프레임당 오버헤드 +1B/멤버(고정형) · 판독기에 tag→setter 디스패치 테이블 · 생성기 난이도 중간.
- 위험: 태그 재사용 금지 규약(진단 MSGPROT 신규로 태그 중복·삭제 경고 필요).

### 옵션 B — 프레임 버전 접두 (경량)

- 헤더 뒤 `byte schemaVersion` + 각 버전의 판독기를 생성기가 전부 유지.
- 모르는 버전 → 현재 버전 판독기가 최선 시도(실패 시 거부). A 대비 구현은 쉽지만
  **삭제된 필드** 내성은 없고 버전 수 선형 코드 증가 — 필드 삭제가 드문 팀에만 적합.

### 옵션 C — 부가 전용 규약 (와이어 무변경)

- 와이어는 그대로, "마지막 멤버 뒤에만 추가 + 수신측 과잉 바이트 무시" 규약 + 진단 지원.
- 구현 최소(과잉 바이트 허용 플래그 하나)지만 **삭제·순서 변경·삽입**은 여전히 파괴적 — 반쪽짜리.

**권장: A.** 이유 — 게임 서버의 실제 변경 패턴(필드 추가가 압도적이지만 삭제·이동도 발생)을
구조적으로 흡수하고, DS_RPC 상위에서도 요청/응답 스키마 진화에 그대로 재사용된다.

## 마이그레이션 (하위호환 전략)

1. **공존 기간**: 같은 타입에 `[VersionTolerant]` 옵션 부여 시에만 태그 형식으로 발행(기본은 현 위치 기반 유지).
   판독기는 **양쪽 형식을 모두 인식**(첫 바이트 태그 판별 비트) — 혼합 피어가 통신 가능.
2. 전환 완료 타입부터 태그 전용. 위치 형식은 다음 major 에서 제거 후보로 명시.
3. DS_RPC 는 자체 와이어(요청 헤더)와 무관하게 페이로드에 MessageProtocol 을 쓰므로 상위 영향 없음.

## 검증 계획 (구현 시)

- 태그 Skip 정확성: 상위 버전 프레임 → 하위 판독 (퍼저에 "버전 차 프레임" 코퍼스 추가).
- 태그 중복/삭제 진단(MSGPROT 신규 ID — AnalyzerReleases.Unshipped.md 행 추가 규약 준수).
- 성능 기준선 재측정: 위치 기반 대비 판독 오버헤드(예상 +30~60%) — Performance-Baseline.md 갱신.

## 대안적 후보 (같은 맥락에서 검토된 것)

- `IBufferWriter<byte>` 진입(송신 버퍼로의 무복사 핸드오프, 104B→32B→0B 할당 사다리):
  와이어 무변경·minor 가능하나 DS_Communication 송신 경로가 `byte[]` 기반이라 현재 수요 미확정 —
  수요 확정 시 별도 제안으로 승격.
